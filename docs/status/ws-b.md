## Thu 9 Oct (Day 8)
- **Done:** the LLM generator, through Tencent Cloud ADP (`brain/gateway/adp.py`). The organizer's guide gives an ADP agent an Experience URL and an AppKey, not an OpenAI-compatible endpoint, so the gateway got an adapter for ADP's Chat API: the context packet is the one message, our JSON-claims instruction goes in `SystemRole` (overriding the agent's prompt for the turn), online search is disabled per turn, the reply is read from `response.completed` (or the streamed deltas), fenced or wrapped JSON is tolerated, and any error, throttling (one retry) or reply without claims is an abstain with the error code logged, never content. `GENERATOR_BACKEND` selects adp, openai or template; `auto` takes the first configured. The agent runs GPT-5.6 Terra (the picker's name, used as the audit label) with no knowledge base and search off.
- **Probed** (`python -m brain.gateway.probe`, check #1, ADR-001): reachable, 3 of 3 replies as JSON claims citing only packet documents, 2.9 to 13.9 s per call.
- **Tested:** 14 adapter tests against a fake Chat API. With ADP generating: all nine golden cases pass on the real pipeline in fixture mode (41 s), zero canaries across every persona and question (45 asks), chain verifies; on the real index with the simulators and real Slack and Drive, the seven non-scripted cases pass with grounding 1.0 on every answer, 4.5 to 17.7 s per question. Answers are now real prose with citations, for example scenario 1: "The database migration is currently in progress but blocked due to replica lag exceeding the 5-second threshold. Last week, blockers raised in Slack included replica lag as the main issue and a slow staging snapshot restore."
- **Changed in the fixtures:** scenario 2's golden rule now checks the new fact ("standby payment region") instead of the heading "failover step", which a real model paraphrases. Not a leak or a wrong answer; flagged here because the fixture is A's.
- **Seen and understood:** the model answers `"claims": []` with a one-line "the evidence does not contain X" when an asker's visible candidates do not cover the question (Jordan or Maya asking for the breach report). That is the right behaviour: it becomes an abstain, and it depends only on documents the asker may see.
- **Done, afternoon:** checker layer 2 (`brain/checker/layer2.py`): a local cross-encoder scores each claim against the evidence it cites; claims under the threshold are dropped, the answer is rebuilt from the rest, and the per-claim scores and model name go into the audit event (`checks.grounding_model`, `checks.grounding_scores`). Check #2 measured on this laptop with `python -m brain.checker.timing` (40 labeled pairs from fixture text): `nli-deberta-v3-xsmall` 44 ms per claim, 0.9 GB, accuracy 0.90 at threshold 0.05, chosen; `nli-deberta-v3-small` 141 ms, 0.72; `MiniCheck-DeBERTa-v3-Large` 1.3 s per claim, 2 GB, 0.97, kept for offline grading. The 3B to 8B chat model for layer 3 was not timed: no memory or runtime for it here; the deployment server's job. Models cached in `HF_HOME` on D:. Recorded in ADR-003 and check #2. Found while validating: the NLI model rejected true claims (4 permille) when the premise was a 600-character snippet, so each claim is now scored against the title plus sliding three-sentence windows of its cited evidence, best score wins (990 and up on the same claims, about 0.3 s for three claims). With ADP generating and layer 2 checking, all nine golden cases pass.
- **Done, evening:** conversations are rebuilt from the audit log instead of a dict in the process, so the sidebar history survives a restart of `make brain-api` (`ask` events now carry `conversation_id`; audit-event-schema 0.1 and api.md 0.2 updated). `GET /v1/conversations/{id}` reopens one of the caller's own chats with every turn; someone else's and a nonexistent one get the same 404. A reopened answer is a derived artifact: it is shown again only if the asker may still open every cited document (stored label plus a live check), otherwise the turn keeps its question and the answer is withheld without naming what was revoked. In the UI each Recent entry is a link to `/ask/<id>` that reopens the chat and continues it. Three API tests (restart, reopen, withheld after e2), a sidebar test, and a browser run on the fixture pipeline. Fixture mode and the stub still keep the log in memory, so only Postgres mode persists; the My Work alerts still use the in-process dict.
- **Fixed, night (found by C's Playwright run on the real API):** concurrent questions failed at the retrieve stage with `OutOfOrderTransactionNesting`: the vector leg opens a transaction block for its `SET LOCAL` on the one shared Postgres connection, and two request threads entered it together (the split-screen asks as three people at once; two of the three streams got `pipeline_error`). A lock around that block in `brain/retrieval/index.py`, like the audit store's; a test runs eight searches at once on both index readers.
- **Seen (C's run):** scenario 1 on the real index cites the Slack thread in 2 of 5 asks. The generator writes the claim every time; layer 2 scores it 18 to 30 permille in the other three (993 and up for the Jira claim) and drops it, so the answer and its citations lose the Slack half. The claim is a paraphrase of a one-sentence message; worth a look at the windowing or the threshold for short evidence.
